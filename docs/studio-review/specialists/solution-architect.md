## 3. Asked for specifically

**Structure and data flow.** main holds the website (React/Vite, static on GitHub Pages) and the collectors. The collectors are scripts in script/ that use api/_scrapers.ts and _national.ts. GitHub Actions runs them every 3 hours and publishes events.json and events-usa.json next to the website. Separately, hotel-towns.yml writes the list of towns each day; a Claude routine outside the repo writes hotel-prices.json to the hotel-data branch, and pages.yml publishes it. The phone app (mobile-app branch, mobile/) reads those JSON files straight from GitHub Pages, so there is no server to run. Accounts, friends, Going sharing, archer-added shoots, the marketplace, messages and push tokens are in Supabase. Supabase sends push notifications through Expo's push service using pg_net. Hand-entered marquee shoots go in main:data/manual-events.json. The design is simple and cheap. Its weak points are the two-branch split and the duplicated code.

**Dependencies.** In mobile/, Expo, React Native and expo-* are all one SDK set (54), three major versions behind (see the table). supabase-js and RevenueCat are current. Android targets API 36 (node_modules/react-native/gradle/libs.versions.toml:4), which meets Google Play's current target-API rule. On main, React 18 (19 is current), many Radix packages are slightly behind, and the server-side packages are unused. `npm outdated` worked through the proxy.

**Offline (no signal at a range).** What works: the last schedule loads instantly from the phone, with an "Offline, showing the schedule from …" banner (CalendarScreen.tsx:678). Stars, reminders, Add to Calendar and hotel prices for each town also work offline, and ads just don't show. What doesn't work: archer-added shoots (see the table), the marketplace, messages, friends, and changing who can see a Going. Those need signal. Saves made offline fail with an error message; they are not queued to send later.

**How hard is it to maintain?** Moderate. The app code is clean, well commented and typed: about 9,500 lines, and tsc passes. The cost is in the setup around it: two branches with copies of the same code, a database with no migrations, a 3-SDK upgrade backlog, a hand-written native patch, and no tests. Fix those (rows 1-7 above) and one developer can maintain it comfortably.

**Is Expo / React Native a good fit, or is a rewrite needed?** It's a good fit. Don't rewrite. It's one TypeScript codebase for iPhone and Android, the app is mostly lists, forms and Supabase calls, and every native piece it needs (AdMob, RevenueCat, Sign in with Apple, calendar, notifications, location) has a maintained Expo or React Native library. `expo prebuild` plus the local Xcode and Gradle scripts already gives Mac-mini-only builds with no Expo cloud. A native rewrite would roughly double the code and the work for no benefit to users. What it needs is the SDK upgrade and the cleanup above.
