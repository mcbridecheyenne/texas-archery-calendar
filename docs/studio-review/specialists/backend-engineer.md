## Secrets scan (no problem found)

- Keys in the app are all public client keys, which are fine to ship. Supabase uses the `sb_publishable_…` key. RevenueCat uses `appl_…` (public SDK key). The rest are AdMob unit IDs and the Stay22 affiliate id (mobile/config.ts).
- I ran `git log --all -p` on both checkouts (78 and 26 commits) and grepped for service_role, sb_secret_, sk_live/sk_test, PRIVATE KEY, AuthKey_/.p8, ghp_/github_pat_, AKIA, xox, JWTs, re_/SG. keys and hard-coded passwords. No project secrets turned up. The only hits were three Google Maps keys inside third-party organizer web pages saved by old commits (`probe-out/html/www_bananabendarchery_club_.html` in 354f529, `stats/out/javascript-root.js` in 273cb1a and 05c71a5). Those belong to other sites, not to us.
- No .env, keystore, .p8, google-services or service-account file was ever committed. .gitignore covers *.jks, *.p8, *.p12, *.key, .env and firebase-adminsdk JSON. The Android signing passwords are read from ~/.archery-keys on the Mac (mobile/scripts/android-release.sh:6-8, 46-48).
- The workflows on main use no secrets at all, only GITHUB_TOKEN with small permission scopes. `npm ci --ignore-scripts` is used.

## Things that look good

- RLS is on for every table. Blocking is enforced in the database. Bans are guarded against self-unban (schema.sql:57-70). `send_push` is revoked from all client roles (:844). Push tokens can only be added through a function (:771-807). All security definer functions set `search_path`.
- Account deletion cascades from `auth.users` to profiles, listings, conversations, messages, friendships, going, community events, push tokens and reports filed (all `on delete cascade`).
- Only the birth month and year are asked, and only `age_confirmed_at` is stored. Location is rounded to about 3 miles and only used while the app is open (mobile/src/lib/location.ts:12-15). Photos are re-encoded by ImageManipulator, which removes EXIF and GPS data.

## 3. Role-specific answers

- **Personal data collected:** Apple ID or email (auth). Display name, city, archery class, home state, join date. Age-confirmed timestamp only; the birthdate is not stored. Friend graph. Starred shoots with dates, including "Just me" ones (see the policy finding). Marketplace listings with photos and lat/lng rounded to about 3 miles. Chat messages. Reports and blocks. Expo push tokens. Organizer phone and email on archer-added tournaments, which are public and may be typed in by someone else.
- **Account deletion:** the database side is complete through cascades. Storage cleanup depends on the phone and is best-effort. The Apple token is not revoked.
- **Moderation:** report, block, ban, and a client-side word filter are present, which covers Guideline 1.2 at a basic level. The gaps are no report alert, removed photos staying public, easy ban evasion, and no server-side limits.
- **Costs that grow with users:** Supabase storage and egress for listing photos is the first limit to be hit. Free is 1 GB storage, and the README says about 800 listings. After that come database rows from messages, and Realtime connections (one per open chat or inbox). Expo push and pg_net cost nothing. GitHub Pages serves the JSON feeds, with a soft limit of 100 GB a month. Plan on Supabase Pro ($25/month) at launch.
